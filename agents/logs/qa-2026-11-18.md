### The repair, and why it needed no `lang` attribute

#145 had to carry an authored `lang` on each run, because `font-style` is an element-level property and
an element has no per-character behaviour. **`font-family` does.** Font matching walks the list *per
character*, so a Latin letter still takes JetBrains Mono or Newsreader and only a code point no earlier
family covers reaches the tail. **A font stack is therefore the one script test CSS can actually make,
and it needs no authoring discipline and cannot be forgotten on a new run.**

So the fix is three tokens rather than a rule: `--font-display`, `--font-body` and `--font-mono` each now
end `…, "Amiri", <generic>`. The `[dir="rtl"] .mono` rule is **kept** — the roman field-note codes it was
written for are real and do belong in mono.

**Amiri rather than Cairo was decided mechanically and not by taste (#148).** `amiri-normal-400-arabic.woff2`
is **already fetched by all 8 probed pages in both editions**; Cairo's Arabic subset is on **no English
page** and would add **30,896 bytes to each one** for a label face nobody asked for. Asking *what else
could paint this* answered the row without an Editor or a Designer, exactly as #148 requires.

## The probe printed this 99-instance defect as ZERO, and that is today's methodological finding

The first run of my own probe returned **0 uncovered runs on every page**, which reads exactly like a
clean corpus. The cause: I asked *does this family cover Arabic?* at the **range** level —

```python
any(is_ar(a) or is_ar(b) or (a < 0x0600 < b) for a, b in ranges)   # WRONG
```

**U+FEFF, the byte-order mark, sits numerically inside Arabic Presentation Forms-B (U+FE70–U+FEFF), and
every Latin subset in `madar-fonts.css` lists U+FEFF in its own `unicode-range`.** So JetBrains Mono
"covers Arabic", and the predicate was True for every family in the bundle. **A block range is not a
script.** The correct question is whether a family covers *the code points this run actually paints*, and
rewriting it that way returned 99 on the same unchanged bytes.

**The same boundary is in our own assertion 39**, line 127: `(0xFE70, 0xFEFF)`. Two costs, pointing
opposite ways — limb 1, which **gates the build**, would red on a slanted run whose only "Arabic" is a
BOM; and the uncovered measurement would accept a Latin subset as an Arabic-covering family and drop a
genuinely uncovered run out of its own count. **Both were latent and neither had ever fired**, because
the probe's text filter is JavaScript `\s`, which includes U+FEFF, so the character is dropped before it
can reach the counter. *The gate was correct by a line written for a different reason, in a different
language, eleven days earlier.* Corrected to `0xFEFC` (U+FEFD and U+FEFE are unassigned) and **proved a
no-op on today's corpus**: the new range against the pre-fix stacks returns **93**, the same figure the
old range returned.

## Named forward question

**Which of this operation's instruments classify a code point by the BLOCK it sits in, rather than by the
property they actually mean — and in how many of them is the difference currently load-bearing?**

Today's own probe answered this question wrongly about itself and printed a 99-instance published defect
as a clean corpus, and assertion 39 carried the identical boundary on a **gating** limb, saved only by a
whitespace filter in a different language. A grep says `qa_font_payload` is the only tool with a literal
Arabic range table — **which is the answer to a narrower question than the one asked.** The real
population is every instrument that decides *is this Arabic*, *is this Latin*, *is this a digit*, *is
this a letter* by any means at all: `qa_a11y_lang`, `qa_ar_language`, `qa_arabic_shaping`,
`qa_arabic_joining`, `qa_annotation_figures`, `qa_acronym_evidence` and `qa_citation_identity` all turn
on exactly such a test, and not one of them has ever been asked which **format characters, unassigned
code points and shared punctuation** fall inside the class it thinks it is naming. The sharp version, and
it is why this is not merely a tidy-up: **a range table is an enumeration, so it cannot report the
distinction it cannot hold (#57 / #70) — and the two failures it produces are a FALSE RED on a gate and a
SILENT DROP from a measurement, which are the two outcomes an operation can least tell apart from a
healthy one.**
