## 2. The defect

Arabic is cursive. `letter-spacing` pulls the joins apart and the word stops being a word.

The stylesheet **already knew this** and had it written down — `letter-spacing: 0` on
Arabic `h1`–`h4`, in the RTL block, since the site's first build. Tracking is not a
property of headings. It is a property of the script, and the script appears in forty
other places.

|---|---|---|
| Arabic home | 64 | **23** |
| Arabic article | 59 | **19** |
| Arabic editions | 143 | **89** |
| Arabic browse | 37 | **9** |
| **English home** | 15 | **4** |
| **English article** | 7 | **4** |
| VALENCE | 1 | **1** |

Nav labels, kickers, country and date spans, the footer rights line, the Still's caption
— and on the **English** side the language switch `العربية`, the cross-language rail and
the wordmark fallback.

**The worst instance had no component to be filed under.** VALENCE sets
`letter-spacing:.005em` on **`body`**; its one Arabic run inherits from a rule naming no
class, no element and no language. There is nothing for a selector audit to audit. **This
is the whole argument for reading computed style rather than CSS text**, and it is #55's
LAYER question: a check can enumerate every file, prove its bite and print its input, and
still read a layer at which the defect does not exist yet.

**And it is #50 with exact arithmetic.** The 08-18 fix removed tracking from the Arabic
wordmark on the VALENCE **share card**, correctly and completely — *for the card*. The
page one directory away kept the defect for another thirty days.

## 3. The fix, and the proof

```css
:lang(ar) { letter-spacing: normal !important; }
```

Keyed to **language**, not to `[dir="rtl"]`, because the Arabic runs on the *English*
pages sit inside a Latin layout. The only `!important` outside the print block, because a
component that tracks its Latin form must not win it back on an Arabic run — that is the
ruling restated in CSS, not a cascade convenience. The same rule added to
`web/public/valence/index.html`, which the build does not touch.

**Proved four ways, per #35 with the 09-14 discipline — every injection asserted to have
changed the artefact *before* the check was run on it:**

| | Injection | Result |
|---|---|---|
| **Control** | none; the real 120-page build | **exit 0** — 7 targets, **326** Arabic-bearing elements, every one `normal` |
| **Bite A** | the fix deleted from the built CSS | **exit 1 — 148 defects** |
| **Bite B** | fix left in place; a higher-specificity `!important` rule added | **exit 1 — 46 defects** |
| **Bite C** | an Arabic page stripped of Arabic letters, CSS untouched and correct | **exit 1** — *found 0, expected at least 20* |

**Bite A's count is its own proof.** 148 = the 149 originally found **minus VALENCE**,
whose fix lives in a file bite A did not touch. A bite that fires with an unexplained
number has been observed, not proved.

**Bite B exists because of the `!important`.** Without it the check could have been
passing on the presence of our own rule rather than on the computed value. B adds a rule
that outranks the fix and the check catches it, which is the property that matters.

**Bite D, added after the push and before the deploy could run.** The per-page browser

**Bite C is the non-vacuity floor.** A tracking-only check reports CLEAN on a page with no

## 7. Forward question for the next run, per the 08-23 rule

**It is the residue of today's, and stating it honestly is the point.** Assertion 17 proves
no Arabic run is **tracked**. **It does not prove the glyphs SHAPED.** A missing font, a
broken `font-feature-settings`, or tofu would pass it in silence, because computed style
reports what was *asked for*, never what the font *delivered* — which is #55's own LAYER
question applied one layer further out than today's fix reached.

The candidate, with its obstacle named so tomorrow does not rediscover it: **measure text,
not pixels.** Render one known Arabic string at a known size and compare its advance width
against the same string with `letter-spacing` forced, using the browser's text-measurement
API. A correctly shaped cursive run is **narrower** than its unshaped letters; if the two
widths agree, nothing shaped. The control this operation does not yet have is a
**deliberately missing font family** — prove it there first, because a check for "the font
worked" that has never seen a font fail is a green light wired to nothing.
