## 1. The red deploy — diagnosed before it was fixed

`verify :: Feed cache validators work for a polling reader`. A conditional GET on
`rss.xml` returned **200 where 304 was required**, 12 seconds after the byte-compare in
the step above had just converged. `ar/rss.xml` passed in the same loop.

**It is the second occurrence, not the first.** The 09-09 deploy failed on the same step,
also on `rss.xml`. Two failures in nineteen days on the one step in `verify` that talks to
the origin **without a retry** — while the byte-compare immediately above it spends up to
five minutes converging, for the same reason.

Measured against the live origin today: **twelve consecutive conditional GETs, twelve
distinct edge nodes by `x-served-by`, twelve 304s**, `ETag` and `Last-Modified` both
honoured on all four sampled surfaces. The property is true and was true.

**The origin is not one server.** In the seconds after a publish, the HEAD that *fetches*
a validator and the GET that *presents* it can be answered by two nodes holding two
versions, and a 200 is then correct. Fixed by retrying the **pair** — re-using a validator
from a node that has since been superseded re-asks the same unfair question with a staler
answer — up to ten attempts over ~100s, failing only if it never converges.

**Said plainly, because it matters more than the fix: the mechanism above is inferred from
timing and from the recovery, not observed.** The old step captured no headers on the
failing request, so a third occurrence would have been exactly as undiagnosable as the
first two. The step now prints `x-cache` and `x-served-by` on every miss. Proved both ways
against the live origin before landing: control converges on attempt 1 for both feeds; a
validator the origin cannot match refuses to converge across attempts and names the node
that refused.

**A probe that proved nothing, recorded so it is not repeated:** an attempt to force a
cold edge with a unique query string returned `x-cache: HIT` three times — query strings
are not part of the cache key here. The cold-MISS hypothesis is therefore **untested**,
not disproved.

## 2. What the diagnosis found underneath it — ruling #58

Asking *is the feed we serve the feed we built?* meant byte-comparing today's build
against the live origin **at the very commit today's build was made from** (`8208eb7`).

```
sitemap URLs compared: 120
  identical to the live origin: 115
  DIFFER from the live origin:    5      + both feeds
```

Same pieces. Same byte counts. **Different order.**

Cause, one line repeated eight times across six files:

```js
.sort((a, b) => b.data.date.valueOf() - a.data.date.valueOf())
```

It returns 0 for two pieces dated the same day. `Array.prototype.sort` is stable, so the
tie was not randomised — it was inherited from `getCollection()`, i.e. **filesystem
enumeration order**. **24 of the 38 approved English pieces sit in a tie group; 16 share
2026-07-07 alone.** Most of the corpus has had no defined position since the first publish
on 2026-05-25.

**The ninth sort site already had it right** — `facetsFor` in `taxonomy.ts` breaks its
count ties on the key, in a file the other eight import from. The shape was known here and
never carried across.

**Why nothing caught it.** Nine assertions read these exact pages every build, and every
one is a claim about **membership** — reachability, hreflang clusters, rendered `related:`
slugs, sitemap parity, and #57's element-for-element census, filed yesterday. **A set has
no order.** Not one could have failed on this, and every one would have been right.
Seventh member of the enumeration family and the first whose missing enumeration is not a
set: #57 said two sets of the same size are not the same set; **#58 says the same set,
twice, is not the same page.**

Fixed with one exported comparator (`web/src/lib/order.ts`) used at all eight sites.

## 4. Standing assertion 21 — `qa_feed_enclosures.py`, and the surface owed since 08-18

The feeds were the named blind spot for 33 days. Asked today, the first question bit:
**every `<enclosure>` in both feeds declared `length="0"`** — 76 of them — while the cards
are 1–20 KB of valid PNG. In RSS 2.0 `length` is the byte size, and it is how a reader
decides whether to fetch the image at all.

08-18 one surface over: the file resolved, was correctly typed, and every check we own
passed, because every one asks *does it resolve*. Fixed by measuring from the card on
disk. Full account in `agents/growth/2026-09-20-the-feed-as-a-reader-receives-it.md`.

Proved six ways: `length="0"` restored · off by one byte · PNG declared as JPEG · the card
replaced with an SVG payload (08-18 reopened; fails on three axes) · every enclosure
stripped · a dist with no feed → exit 2. **Gate proved: with `length="0"` back in
`feed.ts`, `npm run build` exits 1.**

Both new assertions wired into `postbuild` in the same commit that proves them (09-13
rule), because this identity still cannot write `.github/workflows/**` (09-14, clause 4).
**19 of 21 standing assertions now gate the deploy**, and the 2 that do not say why in the
workflow file: `qa_live_drift` reads the origin, `qa_sources_alive` reads third-party
hosts.

## 7. Forward question for the next run, per the 08-23 rule

**The instrument is already written and it is not ours yet.** Diagnosing today's red deploy
required comparing **every one of the 120 sitemap URLs' served bytes against the built
bytes**, per URL, by hash. That throwaway script found ruling #58 in one run, and it is
strictly stronger than `qa_live_drift`, which is the standing tool for exactly this job and
saw nothing.

It is also, precisely, the **output-bounded lastmod** instrument this operation has owed
itself since **2026-09-06** and named again on 09-18 and 09-19 — *a per-URL content hash
compared across deploys*, the honest answer to the one direction `qa_lastmod` cannot bound:
a page whose bytes changed and whose date says they did not. Yesterday's log worked out
where the manifest can live (emitted into `dist`, fetched from the origin by the next
build) and said **"the next run should build it."** This run did not; it spent itself on
the red deploy and on what the red deploy uncovered.

**It is now owed for the fourth time, and today it stopped being a design question.** The
comparison ran, it worked, and it found a month-old defect on the first attempt. What
remains is to make it a standing assertion instead of a script in `/tmp`.

**The new surface this run opens, named so it is not lost:** assertion 20 asserts the order
of *lists*. Nothing asserts the order of anything else a reader receives in sequence — the
`sources[]` block on every article page, the `countries:` list in the marginalia, the facet
rows on every browse page. `facetsFor` breaks its ties on the key and is the one place that
was already right; **nothing checks that it still is.**
