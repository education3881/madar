## 2. The forward question, tested before anything new was added

**Carried from `qa-2026-09-20.md` §7:** *assertion 20 asserts the order of lists; nothing asserts
the order of anything else a reader receives in sequence — the `sources[]` block on every article
page, the `countries:` list in the marginalia, the facet rows on every browse page. `facetsFor`
breaks its ties on the key and is the one place that was already right; nothing checks that it
still is.*

**Tested. Two of the three cannot permute; the third was not right.**

- **`sources[]`** — rendered by `.map` over the frontmatter array; a map preserves order by
  construction. Verified rather than assumed: **76 article pages, both languages, served source
  order against frontmatter order, 0 mismatches.**
- **`countries:`** — `.join(', ')` over the same array. Same reasoning, same result.
- **facet rows** — sorted, by `b[1] - a[1] || a[0].localeCompare(b[0])`. **`localeCompare` with no
  locale argument asks ICU for the default locale, and ICU reads it from the environment.** Same
  code, same keys, three runners:

```
LC_ALL=en_US.UTF-8   ->   … Tunisia, Türkiye, Turkmenistan, Tuvalu
LC_ALL=sv_SE.UTF-8   ->   … Tunisia, Turkmenistan, Tuvalu, Türkiye
LC_ALL=tr_TR.UTF-8   ->   … Tunisia, Turkmenistan, Tuvalu, Türkiye
```

**`Türkiye` has been in this corpus since 2026-07-07.** It is kept out of the sorted set today by
one threshold — a country enters the browse surface at two pieces — which is a fact about how much
we have written, not a guarantee. **Ruling #59.**

The same read found **`facetSlug('Türkiye') === 't-rkiye'`**: `[^a-z0-9]` does not know what `ü`
is, so it becomes a separator. Not live (the page does not exist), and it would have been the
URL the day it did.

## 6. Forward question for the next run, per the 08-23 rule

**Named surface: the sort key that is not the sort key.**

Three rulings now cover *how* our lists are ordered — #57 (by which set), #58 (by which tiebreak),
#59 (decided by what). All three are about the comparator. **Nothing has looked at the other side:
the value the comparator is handed.** Every dated list in this publication sorts on
`data.date`, a `z.coerce.date()` of a bare `YYYY-MM-DD` string with no timezone — which
`coerce.date()` parses as **UTC midnight**, on a runner whose clock is UTC, for a publication whose
calendar is **Asia/Dubai**. Every comparison we have proved is a comparison of the right values
*if and only if* that coercion means what we assume it means, and nothing in the repository has
ever read a parsed date back out and asked what day it thinks it is.

The question to test tomorrow, before adding anything new: **does any surface — the sitemap's
`lastmod`, the feeds' `pubDate`, the rendered `<time>`, the ISO-week cadence row in the stats
panel — disagree with the frontmatter about which day a piece was published, for a piece whose
date sits near a boundary?** The cheapest probe is the stats panel's own week buckets against the
frontmatter dates, and it costs one script.
