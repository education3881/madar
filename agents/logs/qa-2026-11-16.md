**Class B is not emphasis at all.** The English body writes *ranging from Nature to Britannica to
Cambridge* with no asterisks; the Arabic body writes `*Nature*`. The composer is using markdown's only

asterisks. **So #115's de-slanting deleted two different messages, and only one of them was emphasis.**

And item 107's own prescription cannot reach Class B: `Nature` and `Elsevier` are English words on an
Arabic page, so tagging them `lang="en"` and slanting them would make the Arabic edition italicise
company names the English edition sets upright — **a new disagreement between the editions, created by
the repair.** Class B is therefore **not repaired here** and goes to the Arabic Editor as a judgment with
its measurement, because the question is whether a redundant boundary marker should be carried at all.

## THE FOUR THAT REFUSED: an 87-artefact defect in BOTH editions, 50 EN and 37 AR

The four were `bo`'s one and `vietnam`'s three. `e.matches('[dir="rtl"] .body-main em[lang]')` returned
**true** on every one of them and the computed style was still `normal`. Enumerating every rule in every
served sheet that both matches the element and declares `font-style` found **a fourth "not italic" rule
that nobody had enumerated** — and #115's own comment in `global.css` names three point fixes:

```
[dir="rtl"] em, [dir="rtl"] i, [dir="rtl"] cite            => normal   (0,1,1)
[dir="rtl"] .body-main em[lang]                            => italic   (0,3,1)   ← today's
.body-main[data-astro-cid-…] em                            => normal   (0,2,1)
.body-main[data-astro-cid-…] p > em:only-child             => normal   (0,3,2)   ← wins
```

**It is the footnote rule**, in both article templates, and its intent is the dagger note a drafter
writes as `*† Names marked with a dagger are…*` — a paragraph that **is** one emphasised run. It is
styled `display:block`, muted, 10.5px (EN) / 15px (AR), with a 25.5px top margin.

**`:only-child` cannot express that intent, because it counts ELEMENT children and ignores TEXT nodes.**
So these two are the same selector:

```html
<p><em>† Names marked with a dagger are…</em></p>              ← intended
<p>Tuition in Vietnam — <em>học phí</em> — is a monthly…</p>    ← an accident
```

**It catches Arabic phrases as readily as Latin ones** — `تيين فونغ`, `هيئة التحرير` — so it is **not a

### The repair: the boundary moves out of the stylesheet and into the build

The boundary is exact and the artefact supplies it: **does the `<em>`'s own text account for the whole
paragraph?** That is a comparison between an element's text and its parent's — **CSS cannot make it**
(no text-node selector, no content comparison) and the **build can make it trivially**. So:

- `web/src/lib/footnoteParagraphs.mjs` — a rehype plugin, no dependency, the hast tree walked by hand.
  It marks a `<p>` `.footnote-para` when its only prose content is one `<em>`.
- `astro.config.mjs` gains `markdown: { rehypePlugins: [footnoteParagraphs] }` — the build's **first**
  rehype plugin.
- Both templates re-key from `p > em:only-child` to `p.footnote-para > em`.

**The boundary is prose, not text, and the gate found the one-character error.** The first draft demanded
the `<em>` account for *every character* of the paragraph. The corpus's sign-off is written
`— *The Editors*`, and **an em dash is furniture, not prose** — so the sign-off lost its footnote
styling on all 45 English pieces and **`qa_render` failed the build** on a *130-row blank band* where it
had been. Widened to *no letter and no digit outside the run* (`/[\p{L}\p{N}]/u`). **A boundary drawn one
character too tight reads exactly like a boundary drawn right**, and only a gate that looks at the raster
could tell them apart.

### Proved both ways, and two independent boundaries agree exactly

- **Partition.** 166 matches → **79 marked** `footnote-para`, **87 not**. An independent classifier
  written before the plugin (comparing paragraph text to run text) split the same 166 into **79 / 87**.
  Two methods, one answer.
- **Bite cleared.** `Lan fɔ lan.` → `display:inline`, **19px**, *italic*, `rgb(14,27,44)`, `margin-top:
  0`. `học phí` / `học thêm` / `lạm thu` likewise.
- **Control held.** `† Names marked with a dagger are…` and `A placement seats the child…` still render
  `display:block`, 10.5px, muted, 25.5px margin — unchanged. The sign-off `— The Editors` and
  `— هيئة التحرير` are footnotes again.
- **And it closed item 107's remainder.** Freed from the footnote rule, the four stragglers compute
  italic: **item 107 is 30 of 30 on the runs this repair covers**, with Class B and Class C recorded
  above as judgments rather than as debt.

### A build-cache finding worth more than it cost

The rebuild after widening the boundary reported **the same 33 pages** as the build before it, and the
sign-off was still unmarked. The predicate was right; **Astro's content cache had served the previous
build's markdown output, because a rehype-plugin change does not invalidate it.** Had the count not been
watched, the correct fix would have been read as a failed one. `rm -rf node_modules/.astro .astro dist`
and the count went 33 → **49**. *A pipeline change can be reported on by a cache that never ran it* —
raised as item 120.

## The forward question — what this sweep cannot structurally see

**Every rule in this stylesheet is a claim about the corpus, and nothing anywhere states which claim it
is.** Today's defect was not found by a gate. It was found because a *different* repair lost a
specificity fight, and the only reason it was findable at all is that I enumerated the matching rules in
a browser **by hand**, on one element, after being surprised. `qa_selector_coverage` asks whether a
selector reaches *a* page — it answered yes for `p > em:only-child`, correctly, on all 166 matches,
**79 of which it was written for and 87 of which it was silently wrong about.** A selector that matches
too much is indistinguishable, to every instrument we own, from a selector that matches exactly right.

So: **for how many of this stylesheet's 402 asserted selectors does the set of elements it actually
matches differ from the set its own comment or name says it is about?** `:only-child`, `:first-child`,
`em`, `[dir]` — each is a *proxy* for an authorial category (a footnote, a standfirst, a script, a
page), and the gap between proxy and category is where both of today's defects lived, in opposite
directions: #115's selector was **wider** than its fact, and the footnote selector was **wider** than its
intent. The measurable form: for each selector, the count it matches against the count the comment
claims — and a selector whose comment makes no countable claim is its own finding, because *a rule nobody
can falsify is a rule nobody is maintaining* (#144 pointed at CSS).

**Test it before adding anything new.** It enters the board at OPEN's head as **item 121**.
