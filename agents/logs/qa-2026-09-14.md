## 1. The assertion — `qa_css_tokens.py`, the thirteenth

A dist-only assertion, so per the 09-13 rule it is **gated in the same commit that proves it** —
there is no intermediate state where it "runs in the daily." **It is not wired where the other
twelve are, and the reason is a permission, not a preference: see §1b.**

It honours three legitimate ways a `var(--x)` is satisfied: a definition in the built output; an
in-place fallback (`var(--x, #D94F2A)`, which cannot evaporate); and a **runtime setter**, derived
from the built output rather than kept in a hand-written allowlist, so VALENCE's `--c` (set by
`element.style.setProperty`) is correct code and is not cried wolf on. A check that cries wolf is a
check that gets ignored.

**Scope discipline** (yesterday's ruling, trap 2 — an assertion must not read its answer off a
wider field than the one it checks): uses *and* definitions are read from CSS contexts only — whole
`.css` files, `<style>` blocks, `style="…"` attributes. A `--word:` in an article body is text, not
a token, and is not allowed to satisfy anything.

## 1b. Where the gate actually lives, and why it is not beside the other eleven

The assertion was written into `.github/workflows/astro-pages.yml` beside the others, exactly as the
09-13 rule requires. **The push was rejected:**

```
! [remote rejected] HEAD -> main (refusing to allow a GitHub App to create or update
  workflow `.github/workflows/astro-pages.yml` without `workflows` permission)
```

The autonomous run authenticates as a GitHub App, and a workflow file is the one thing that
identity may not write. This is not grantable from inside the workflow — the `permissions:` block
has no `workflows` key, by design, because a job that can rewrite its own workflow can grant itself
anything. **The design is correct and the constraint is real**, which makes it the interesting kind
of problem: the operation moved to the cloud this morning in order to stop depending on one person,
and discovered the same afternoon that one class of change still does.

**The gate was not dropped and the rule was not weakened.** `npm run build` is precisely what the
deploy job runs, and npm runs `postbuild` immediately after `build`. So the assertion is invoked
from `web/package.json`:

```json
"build": "astro build",
"postbuild": "python3 ../agents/tools/qa_css_tokens.py dist"
```

A failure there fails `npm run build`, which fails the build job, and nothing deploys. Proved
through that entry point rather than argued:

| Experiment | Result |
|---|---|
| `npm run build` on the real tree | **exit 0** — 174 files, 69 read, 77 defined, 1 runtime |
| `npm run build` with today's defect reinjected **at source** (`var(--color-accent)` back into the browse page) | **exit 1**, naming the token |
| restored, `npm run build` again | **exit 0** |

In one respect this is *stronger* than a workflow step: it also gates every local build, so the
defect cannot be introduced on anyone's machine and discovered in CI. What it costs is legibility —
`astro-pages.yml` has been the single readable register of what gates the deploy, and today it stops
being complete. That is a real cost and it is the reason this is not being treated as the permanent
answer. Filed as a founder decision, because the clean fix needs a credential only he can create.

## 4. Forward question (required per the 08-23 ruling) — for the 2026-09-15 run, before anything new

Today's check proves a custom property **resolves**. That is the same verb the link sweep, the
orphan sweep and the hreflang sweep all use, and 2026-08-18 already taught this operation that
*resolves* is a narrower enumeration than *works* — the og:image resolved perfectly for 83 days and
rendered nowhere.

**Named surface for 09-15: nothing this operation owns has ever checked that a page RENDERS.**

All thirteen assertions read structure — a thing is present, resolves, parses, matches, agrees.
Not one has looked at a pixel. The evidence that this is a real gap rather than a theoretical one is
already in the record: the Arabic wordmark's broken letter-joins on the VALENCE share card (08-18)
were found by a human opening a PNG, the daily brief rendered edge-to-edge for two days (08-16 →
08-18) and was found by someone happening to look at one, and today's defect was *visible to the
eye and invisible to every check* — a country label in the wrong colour on 76 pages. Three
render-class defects, three accidental discoveries, zero instruments.

The candidate is a render check with a deliberately narrow first scope, because the wolf-cry risk is
high: take one built page per language plus one share card, rasterise headlessly, and assert the
cheap invariants that have actually bitten — a non-empty body box, text that is not white-on-white,
Arabic glyphs that join, and a computed accent colour that is not the inherited ink. The open design
question, which is why this is a question and not a task: **a render check has no stable oracle** —
a screenshot diff fails on every legitimate edit, so the assertion has to be about *properties* of
the rendering, not its identity. Naming the properties worth asserting is the first half of the
work, and it is the half that decides whether this becomes a gate or another habit.
