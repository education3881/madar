## Item 96 — CLOSED on the sitemap half, and the JSON-LD half is raised as its own row

**What shipped.** `agents/stats/served-dates.json`, a committed per-URL register of the date each page's
own **normalised served bytes** last changed, maintained by `agents/tools/served_dates.py`, and
`web/src/lib/sitemapLastmod.mjs` now reads it in preference to git provenance. Git provenance remains the
fallback for a URL the register has never seen — which is exactly a page being served for the first time,
where provenance is the right answer.

The operand is `qa_served_manifest`'s existing `content_sha`, **imported from that module rather than
reimplemented**: two normalisers independently deciding what "the page says" means is a drift defect this
repository has already paid for twice.

**The result, measured on the built sitemap rather than argued:**

| | before | after |
|---|---|---|
| distinct `<lastmod>` dates across 138 URLs | **2** | **17** |
| URLs in the single largest date bucket | **~120** | **49** |
| dates moved by a one-sentence edit to one article body | **49** (that page + all 48 listing pages) | **1** |

The last row is the bite, run on the real tree: one sentence appended to
`2026-05-25-bo-teacher-chalk`, **the injection asserted to have changed the file before anything was
measured** (#74), then a full build, then the register read against it — **exactly one page's served bytes
moved**, and it was that page. The listing pages did not move, correctly: a body edit does not change what
a browse page says. Under the retired resolver all 48 of them would have moved, because index pages
resolved as `max(chrome, newest approved content file)`. File reverted, tree confirmed clean, rebuilt
green.

The control is not re-run here because it already exists and re-running it would prove less: the
2026-10-06 probe behind `qa_served_manifest` changed one character in `global.css` and measured **120 of
121 raw page hashes changed, 0 `content_sha` changed**. The normaliser's separation of presentation from
rendered content is the thing this register rests on, and it was proved on the real corpus then.

**Three red builds on the way, and each one was a gate written for something else catching this.**

1. **The stamp was a clock reading.** `changed_at` was taken from wall clock; `qa_lastmod` red on **48 of
   138** URLs within a minute, because its limb 2 bounds every `<lastmod>` by its own URL's provenance
   ceiling and says anything above it "can only have come from a held draft, from build time, or from thin
   air." A clock reading *is* build time. Stamp moved to the **HEAD commit's own timestamp** — the tree the
   bytes were built from — which is both truthful and inside the ceiling.
2. **The seed read its answer off its own prior output.** The 48 pages with no own source file were then
   seeded from the `<lastmod>` the built sitemap already carried, on the stated ground that it *is* the
   provenance ceiling. It was not: that sitemap had been produced by the previous build, which had already
   read the broken register being replaced. `qa_lastmod` red a second time with the **identical 48 URLs and
   the identical timestamp**. This is 2026-09-14's trap 2 — *an assertion must not read its answer off the
   field it supplements* — on a **seeding path** rather than on a check, and it is the 10-06 warning about a
   manifest generated by the build it describes, met head-on. The ceiling is now computed from git.
3. **A page with no own file in `src/content` is not the same thing as a page with no own file.**
   `/madar/valence/` then seeded at the chrome ceiling and red a third time, 9 days above its bound: it is
   built from `web/public/valence/index.html` and from nothing else, so the chrome ceiling is not its
   ceiling. The resolver already knew this and said so in a comment; the seeder had to be told.

**Final state: build exit 0, all 12 build-job gates green, `qa_lastmod` PASS — 138 URLs, 138 lastmod.**

**The seed is a declared known error with a declared size.** Nothing in this repository ever recorded when
a page's served bytes last changed — that is the defect — so the register cannot be derived backward. Per
the 2026-10-04 second amendment's limb two, the register states its opening date and its error rather than
starting clean: 91 entries seeded from their own source file's last commit, 47 at the chrome ceiling, every
one flagged `seeded: true` and clearing on its first real change. **47 of 138 were wrong on 2026-11-10 by
the measurement that raised the row**, and that is the size being carried in.

**What is gated and what is not.** `--check` is offline and deterministic and asserts only the register's
well-formedness and that no date is in the future. Register *staleness* against a built `dist` is
**printed and not asserted** (#93): a build that reds until a side-effecting tool is re-run would red the
**deploy** job, where nobody can re-run it. Wiring staleness as a gate is the next step and is deliberately
not taken before these dates have survived one real deploy — a gate whose determinism across two machines
is assumed rather than proved is the 2026-10-20 shape, where four green local builds sat beside a red
deploy.

**Why the JSON-LD half is a separate row and not a half-done branch.** `<lastmod>` lives in
`sitemap-0.xml` and **not in the page's own bytes**, so the hash cannot see the date and the date can be
derived from the hash. `dateModified` **is** in the page's bytes, so the same move there is a fixed point:
date moves, bytes move, hash moves, date must move again, on every page, on every deploy, forever. Closing
it requires `content_sha` to exclude the self-referential date fields, which invalidates every baseline on
the origin until a deploy re-seeds it. **Raised as item 98.**

## Forward question — what can today's sweep not structurally see?

**The register records WHEN a page's bytes changed and can never record WHETHER the change was worth a
crawler's attention — and we have just spent the operation's only discoverability signal on that
distinction without defining it.** Today's instrument is exact about byte movement and silent about
significance: a corrected typo, a new paragraph of evidence, an Arabic honorific appended to one
annotation under #86 clause 2, and a template whitespace change that survives the asset-hash normaliser
all move `content_sha` identically and will now all move a date. Google's own definition is *the date of
the last **significant** modification*, and the word is doing work we have never once measured. So: **of
the changes this register will date over the next month, how many move a byte a reader would notice?** The
first cut needs no oracle — diff the rendered text content of the two builds, not the markup, and report
the distribution of changed *visible characters* per dated change. If most dated changes move zero visible
characters, we have replaced a 28%-precise signal with a precise signal about the wrong thing, which is
**ruling #138's unit test** pointed at our own repair.
