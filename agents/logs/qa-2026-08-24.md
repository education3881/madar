## 1. Defects found this run — the consumer lens, third consecutive day

Yesterday's brief named three surfaces that had never been asked *what does the consumer actually
receive*. **All three were defective. A fourth was found beside them.** Every one was live for the
entire life of the publication — 91 days.

### P1 — `og:locale` absent on all 82 pages, and absence is not neutral (live 91 days)
**Symptom:** no page declared `og:locale`. **The Open Graph default is `en_US`.** Every Arabic page
has therefore served an Arabic title and an Arabic description to a scraper under an implicit claim
of American English, since the first publish on 25 May.
**Why every check passed:** `<html lang="ar" dir="rtl">` was present and correct on every page. The
document said Arabic. Nothing in the card did.
**This is ruling #33 one surface further out** — markup declaring a language is a claim, *and so is
the claim made by omission.* We had extended the rule to the machine-readable description (JSON-LD)
on 08-23 and stopped one field short.
**Fix:** `og:locale` (`ar_AR` / `en_US`) plus `og:locale:alternate` wherever an hreflang pair
exists. The territory suffix the format demands is a real awkwardness for a publication with no
country; the reasoning is recorded in the source comment rather than buried — `ar_AR` is the
conventional territory-free form for Modern Standard Arabic, and `en_US` is stated only because it
is already the spec's silent default, so declaring it asserts nothing new while making the
alternate pair legible.

### P1 — `og:type` hardcoded to `article` on all 82 pages (live 91 days)
**Symptom:** the English home page, the Arabic home page, About, and both editions indexes all told
every scraper they were a single article. Shared, each invited a reader to "read" a page that is a
list.
**Fix:** new `pageType` prop, **defaulting to `website`** — the fail-safe direction, since a listing
mislabelled as a website is inert while an index mislabelled as an article is a false claim. The two
article routes opt in explicitly.

### P2 — `og:site_name` absent on every Astro page
Present on exactly one page in the build: `/valence/`, which is hand-written and has its own head.
Fixed for the other 81.

### P1 — no print stylesheet had ever existed (live 91 days)
**The question asked was whether an Arabic page prints right-to-left.** The answer was one layer
further out: `grep "@media print"` returned **zero matches in the entire stylesheet**. No page has
ever had print handling.

What a reader actually received on paper or in a Save-as-PDF: the skip link, the top bar, the
language switcher, the share buttons, the related-reading rail, the footer navigation — and, worst
of the set, **a Sources block in which every citation was a coloured word with no URL behind it.**

This matters more here than it would elsewhere. Madār's entire claim is that every piece stands on
named primary sources, and the readers likeliest to print — a ministry adviser, a researcher, a
teacher taking a piece into a room — are exactly the readers who need the citations to survive the
trip. **We were printing the argument and dropping the evidence.**

**Fix:** an `@media print` block that drops the screen furniture, controls page breaks around
headings, stills and pull quotes, and — the point of it — prints the URL after every source
citation, scoped to the Sources list so running prose stays readable.
**Direction:** verified, not assumed. `dir="rtl"` sits on `<html>`, so print inherits it correctly.
That was the original question and it has a clean answer.

### Checked and found CLEAN
- `robots.txt` — `Allow: /`, correct absolute sitemap reference. Unchanged, still right.
- `dir="rtl"` inheritance in print — correct by construction.

## 3. Growth action — sitemap `lastmod`, from git

82 URLs had carried **zero** `lastmod` since the hand-patched sitemap was retired on 07-02, while we
revised all 76 article pages twice in one week. A crawler has never had any signal that this site
changes.

**Two obvious sources were rejected, and the rejections are the substance of the fix:**
- **Build time on every page** — trivial, and worse than nothing. Every page would claim to change
  on every deploy, which is the canonical unreliable pattern; Google discounts a `lastmod` it judges
  unreliable, so we would spend the signal to say nothing.
- **The frontmatter publication date** — that is the *publication* date, and using it as `lastmod`
  asserts the page has not changed since it published. False for every page on this site.

**Used instead: the last commit that touched the files a page is built from.** A real modification
date. A page's date is `max(its content file, the newest chrome file)`, because a change to the
layout, a shared component or the display layer genuinely re-renders every page that includes it —
the 08-23 Arabic fix edited no article file and changed what all 38 Arabic pages say.

Two refinements made after the first working version, both worth recording:
- **`web/src/styles` is excluded from the chrome set.** Presentation is not content. Today's print
  block changes how every page looks and not one word of what it states, so it must not bump 82
  dates.
- **Timestamps pass through untruncated.** Emitting `YYYY-MM-DD` made `@astrojs/sitemap` normalise
  it to `T00:00:00.000Z` — an **invented midnight**, precisely the fabrication the 08-23
  structured-data work refused when it made `datePublished` a date and not a timestamp. Git supplies
  the real commit time, so there was never a need to choose between a truncated date and an invented
  hour.

**Fail-loud, and it closes a live trap.** `actions/checkout@v4` clones at depth 1 by default, and in
a shallow clone `git log -- <path>` returns nothing: this would have passed locally and emitted an
empty `lastmod` in CI — the exact shape of the 07-02 lockfile outage and the reason ruling #16 says
verify in the judging environment. The resolver therefore **throws** on a shallow clone or an empty
map, and `fetch-depth: 0` lands in the same commit. If that line is ever removed, the deploy fails
loudly instead of quietly.

**Verified in the built output:** 82 `<loc>`, 82 `<lastmod>`, real commit timestamps
(`2026-08-23T18:00:03Z` for the corpus, `2026-08-18T05:39:28Z` for `/valence/`, which has its own
life).

## 4. Growth action — the discovery-path audit, and the one number it produced

Full note: `agents/growth/2026-08-24-discovery-path-audit.md`. Recorded here because it changes what
"green" means.

Yesterday Growth committed to checking whether the structured data had indexed. It has not — and the
reason is worse than a delay. **Two searches, including five distinctive phrases from our own prose,
return zero results from the domain. Not one of 82 URLs appears in a search index**, because nothing
on the public web links to the site, Search Console is blocked behind the domain decision, and no
submission API has been called.

Every technical improvement of the last eleven weeks is correct and currently invisible. The
mechanism is that crawlers arrive by link, and there is no edge into this graph.

**Fixed today, autonomously:** the repository README now links to the live site. `github.com` is
crawled continuously and a repository README is indexed, so it is the one page connected to this
project that search engines certainly visit — and it did not contain the URL of the site it builds.
That is the first inbound edge, and it cost one commit. The README was also three months stale
(still "working title", still a five-agent team, folder table predating the guidebook, briefs, stats
and tools); corrected, with the founder's own sentence about what the project is preserved verbatim.

**Not done, deliberately:** IndexNow submission requires an HTTP POST, and Growth does not make
network writes autonomously. Prepared and specified for the founder or the Web Developer.

**First honest growth figure this operation has been able to state: 0 of 82 URLs indexed.**
