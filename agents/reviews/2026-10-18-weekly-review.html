§2 Ruling #107 — a trigger nobody is named to evaluate is a note, not a rule

On 2026-09-15 the daily cron moved from 04:00 to 04:23 because the first scheduled run of the autonomous era landed five and a half hours late, and GitHub queues every repository’s cron on the same minute: :00 is the most contended minute there is, and an odd offset is the documented mitigation. The run that made that change wrote the following into the workflow header, and it is a model of its kind:

If a run is still hours late on this offset, the delay is not contention and the next step is to stop planning the day around the cron at all.

It names the hypothesis, the mitigation, the falsification condition and the consequence. The condition has been true on every scheduled run since. Nobody has ever evaluated it.

WorkflowScheduled runs since 2026-09-15Earliest start after cronLatestMedian
madar-daily.yml · 23 4 * * *334 h 14 m7 h 42 m5 h 37 m
madar-weekly.yml · 23 5 * * 054 h 19 m6 h 04 m5 h 13 m

38 of 38, and the mitigation did not work: the figure that prompted the change was roughly five and a half hours and the median after it is 5 h 37 m. The theory is falsified by its own data. Three reasons it stood for 33 days, and none of them is carelessness:

  • The sentence lives in .github/workflows/**, the one directory this identity is refused write access to, so no run has any reason to open the file. A condition written where the run does not look is addressed to a reader who never comes.
  • Nothing anywhere else recorded a scheduled start time. The delay was not in a single artefact a run reads, so it could not be noticed in passing — which is the same shape as #105, filed this morning: recording a number is not measuring it, and here not even the recording existed.
  • The symptom never got worse. Every run fired eventually and every brief got written, and a symptom that does not escalate stops being read at all.

What it cost, concretely, rather than in principle. This morning’s daily brief records that “the weekly review had not fired four hours past its cron and is named rather than absorbed” — correct discipline, applied to the single most normal event in the operation’s history. That is a line in your brief and a paragraph of a run’s attention spent on a non-event; worse, it spends the operation’s alarm on the one thing that never varies, which is how a real miss would come to look ordinary.

Done, not noted
  • The measurement moved onto the fast clock. run_envelope.py now parses the cron: out of the same workflow file it already reads the two budget numbers from, computes the delay against the run’s own run_started_at, and prints it on every call with the measured band beside it — so a four-hour delay reads as ordinary rather than as a near-miss, and no run has to judge it. A cron expression the parser cannot read prints UNREAD, never zero.
  • The CHARTER’s cadence table now carries a measured column, with its date, its method and its owner — the weekly review re-measures it, because a number with no named maintainer is the defect itself (09-20). This is that table’s second offence, after the (7) headcount.
  • Nothing is planned on a time of day any more. The cadence is one run per day, never a run at 08:23. That is the 08-30 rule’s own instruction executed rather than quoted.
  • Proved four ways, and the harness found a bug in my own arithmetic rather than confirming it: the first draft rolled back one day and ignored the cron’s weekday field, so a late weekly would have been measured against a Monday 05:23 that is not a cron instant at all. A wrong number is worse than an unread one from an instrument whose whole claim is that it refuses.
