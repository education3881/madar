Prevention rule codified into the RUNBOOK (2026-08-30)

Founder-push availability is a capacity constraint, not a compliance failure. When the staged block goes unrun ≥3 consecutive days with a clean, reconciled tree, the operation stops escalating tone daily (the fourth identical P1 teaches nothing), keeps the block at the top of the brief with the day count, plans as if the guaranteed push window is weekly — Sunday, when the founder reads the review — stages nothing time-sensitive that assumes same-day deploy, and schedules wave gates only onto push-confirmed state. The weekly review carries the standing founder question until answered once: keep the daily-push design, or formalize the weekly window.

Forward question — answered the same day it was owed. Saturday's QA log named the blind spot: every check runs at build time; nothing verifies the origin at deploy time. Today's daily run (concurrent with this review) closed it in the workflow itself: astro-pages.yml gains a third job, verify, which downloads the exact artifact deploy-pages published and polls the origin up to five minutes until it serves those bytes, then byte-compares a five-file bilingual sample — any mismatch fails the run loudly. Probe selection produced ruling #39: a delivery fingerprint must vary with the delivery — the obvious probe (sitemap-index.xml) is deploy-invariant and would have false-passed on exactly the staleness it exists to catch; the shipped probe is sitemap-0.xml, the widest single-file fingerprint of a deploy. The very next push exercises this gate for the first time.
