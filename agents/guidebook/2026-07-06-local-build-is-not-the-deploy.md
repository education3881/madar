# Ruling #16 — a passing local build is not a passing deploy

**Date:** 2026-07-06 · **Web Developer / Manager** · **Origin:** the 07-02→07-06 deploy outage (see `qa-2026-07-06.md`)

**The failure shape:** the site built clean locally on three separate days while every production deploy silently failed. Cause: `package-lock.json` committed out of sync with `package.json`; local verification ran `npm install`-based routes (which tolerate and *repair* desync), production runs `npm ci` (which hard-fails on it). The three gates that "passed" were each measuring something adjacent to — not identical with — what production measures. The site sat 11 days stale behind a green-looking operation, and the fix itself sat unrecognized in the working tree for two days, mislabeled "benign."

## The rules (binding)

1. **When dependencies change, the gate runs what the runner runs.** Any commit touching `package.json`, `package-lock.json`, or CI config must pass `npm ci` (from the *committed* lockfile, clean checkout) + `npm run build` before staging — not `npm install`, whose success proves nothing about the lockfile and whose side effect (rewriting the lockfile) can quietly *become* the fix without being recognized as one. If `npm install` changes the lockfile on an ordinary day, treat that diff as a **signal of pre-existing desync**, not noise: something upstream committed a broken pair.
2. **Lockfiles are never hand-edited.** They are regenerated by npm or not touched. A hand-patched lockfile is the drift-defect twin of the hand-patched sitemap (ruling of 2026-06-07): correct the day it is written, silently fatal later — except this one fails the *pipeline*, not the artifact.
3. **Live verification reads an unambiguous deploy marker.** HTTP 200 proves a server; it does not prove *your deploy*. After any push that must change the live site, verify a marker **only the new deploy can serve** (a new URL, a changed robots line, a content hash) — never a count or page that the previous deploy could also plausibly serve. The 07-04 miss read "41 URLs at /sitemap.xml" as the integration's output; the hand-patched predecessor also served 41.
4. **"Deploys are automatic" is a claim about a mechanism, not a fact about the world.** The RUNBOOK's ~90s promise holds only while the pipeline is green — and the pipeline's greenness is only observable from the Actions tab (founder-side) or a live marker (operation-side). The operation's side of that observability is rule 3, every ship-day run.

## Why this compounds

This is the third instance of one meta-pattern, now named: **generated artefacts and their generators must be verified in the form production consumes them** — the sitemap (hand-kept vs build-generated, #06-07), the dek cap (scratch-string vs saved file, #07-04), and now the lockfile (install-tolerant vs ci-strict). The general rule: *verify the thing itself, in the environment that judges it, not a proxy that is easier to reach.*
