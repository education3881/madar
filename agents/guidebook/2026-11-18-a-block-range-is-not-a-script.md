# A block range is not a script — ruling #150

**Filed 2026-11-18** by the daily run's quality function, out of the closure of standing-queue item 40.
**Family:** assertion discipline — **sixty-second member**, and the first whose subject is the
*classifier* an instrument uses rather than the comparison it performs.
**Section 1 row:** 146.

---

## The ruling

**WHERE AN INSTRUMENT DECIDES WHAT KIND OF THING A CHARACTER IS, IT MUST TEST THE PROPERTY IT MEANS AND
NOT THE BLOCK THE CHARACTER SITS IN — BECAUSE A UNICODE BLOCK IS AN ALLOCATION RANGE AND NOT A SCRIPT, AND
THE TWO FAILURES THIS CONFUSION PRODUCES ARE A FALSE RED ON A GATE AND A SILENT DROP FROM A MEASUREMENT,
WHICH ARE THE TWO OUTCOMES AN OPERATION CAN LEAST TELL APART FROM A HEALTHY ONE.**

And the corollary that makes it checkable rather than merely true: **ask the question about the characters
actually in front of you, never about the class they belong to.** *Does this font cover Arabic* is a
question about a range table. *Does this font cover these fourteen code points* is a question about the
artefact, and it cannot be answered by accident.

---

## What happened

Standing-queue item 40 said **89 painted Arabic runs carry a font stack that names no bundled family
covering Arabic.** To close it, this run wrote a probe over served bytes asking, for each painted run,
whether any family in its computed stack covers Arabic:

```python
ARABIC = ((0x0600,0x06FF),(0x0750,0x077F),(0x08A0,0x08FF),(0xFB50,0xFDFF),(0xFE70,0xFEFF))

def covers_arabic(fam, fc):
    rs = fc.get(fam)
    if rs is None: return None
    return any(is_ar(a) or is_ar(b) or (a < 0x0600 < b) for a, b in rs)   # WRONG
```

**It returned 0 on every page.** Eight pages, both editions, every count zero — which reads exactly like a
clean corpus, and would have closed the row as *already fixed* or reopened it as *not reproducible*.

**The cause is one code point.** `U+FEFF` is the zero-width no-break space — the byte-order mark. It is a
**format character**, and it sits at the **top of the Arabic Presentation Forms-B block**, U+FE70–U+FEFF.
Every Latin subset in `madar-fonts.css` lists `U+FEFF` in its own `unicode-range`, because every Latin
subset is generated by a tool that includes the BOM. So *JetBrains Mono covers Arabic* was **true** under
that predicate, and so did every other Latin face in the bundle.

Rewritten to ask whether a family covers *the Arabic code points this run actually paints*, the same
unchanged bytes returned **99**.

## The same boundary was in a gating assertion

`qa_font_payload.py` line 127 carried the identical range, ending at `0xFEFF`, and it is used to compute
`n_ar` — the number of Arabic characters in a painted run. Two consequences, pointing in opposite
directions:

- **Limb 1 gates the build.** It fails on any slanted run containing an Arabic code point. A slanted run
  whose only "Arabic" character is a BOM would have **red the build** on a page with no Arabic in it.
- **The uncovered-stack measurement would go quiet.** `in_any(U+FEFF, bundled[fam])` is true for every
  Latin subset, so a run whose genuine Arabic letters are uncovered but which also contains a BOM would
  satisfy the coverage test and **drop out of its own count**.

**Neither had ever fired, and the reason is the sharpest part of this ruling.** The probe's text filter is
JavaScript `\s`, and ECMAScript's `WhiteSpace` production **includes U+FEFF**. The character is discarded
before it can reach the counter. *The gate was correct by a line written for a different reason, in a
different language, eleven days earlier.* Corrected to `0xFEFC` — U+FEFD and U+FEFE are unassigned — and
**proved a no-op on today's corpus**: the new range run against the pre-fix stacks returns the same **93**
the old range returned.

A defect that is latent because of an unrelated accident is not a defect that has been handled. It is one
whose trigger nobody owns.

## Why this is its own ruling and not an instance of #57

#57 says *count against the population, never against yesterday's number*, and the enumeration family
(#50 and its RUNBOOK siblings) says *a green check is scoped to what it enumerates*. Both are about
**what a check looks at**. This is about something one step earlier: **what a check believes its subject
IS.** The enumeration was complete here — the probe read every text node on every page, and the range
table listed every Arabic block correctly. Nothing was skipped. The classifier was simply wrong about the
edge of its own class, and a complete enumeration under a wrong classifier is **worse** than an
incomplete one, because the coverage figure is honest and the answer is not.

It is the mirror of **#106** (*a check's assumptions about its subject are dated*): there the assumption
had expired, here it was never true.

## Why a block is not a script, stated once so it is not re-derived

Unicode blocks are **allocation ranges**: contiguous spans assigned to a committee's working area, sized
in round numbers, and routinely holding characters that belong to no script or to all of them. Scripts are
a **character property** (`Script=Arabic`), and the two deliberately do not coincide. Three shapes of the
same trap, so the next instrument recognises it without re-finding it:

| Block | Contains | A block test gets wrong |
|---|---|---|
| Arabic Presentation Forms-B, U+FE70–U+FEFF | U+FEFF, the BOM | **this defect** — a format character read as an Arabic letter |
| Arabic, U+0600–U+06FF | U+0600–U+0605 and U+06DD, format characters; U+0660–U+0669, Arabic-Indic digits | a *digit* counted as a letter, which is what every figure instrument we own turns on |
| General Punctuation, U+2000–U+206F | U+200C/U+200D, the joiners **Arabic shaping needs** | an Arabic-shaping check that reads "is this Arabic" would discard the joiner that decides the shape |

The third is not hypothetical for this publication: `qa_arabic_joining` exists.

## Binding

1. **An instrument that classifies a code point tests the property, not the block.** Where a range table
   is used it carries, in a comment at the table, which characters inside its ranges are **not** members
   of the class it names — and `0xFEFF` is the first entry.
2. **The question is asked about the characters present, never about the class.** *Does this family cover
   these code points* beats *does this family cover this script*, and it is the same number of lines.
3. **A classifier is proved with a character on each side of its edge**, in the same way #35 requires a
   bite and a control: for a range ending at a format character, that means one real letter and the format
   character itself.
4. **A latency is recorded with the accident that produces it.** When a defect in an instrument has never
   fired, the run names *what is suppressing it* — here, a whitespace filter in another language — because
   that accident is the thing that can be removed by an unrelated edit, and nobody will connect the two.

## Forward surface, carried onto the queue as item 129

**Which of this operation's instruments classify a code point by the block it sits in rather than by the
property they actually mean — and in how many is the difference load-bearing?** A grep finds exactly one
literal Arabic range table, **which answers a narrower question than the one asked**: the real population
is every instrument that decides *is this Arabic*, *is this Latin*, *is this a digit*, *is this a letter*
by any means at all — `qa_a11y_lang`, `qa_ar_language`, `qa_arabic_shaping`, `qa_arabic_joining`,
`qa_annotation_figures`, `qa_acronym_evidence`, `qa_citation_identity` — and not one has been asked which
format characters, unassigned code points and shared punctuation fall inside the class it thinks it names.
